# AGI Mocap 长运行卡顿调查（2026-09-24）

当前链路：Mocap 屏幕桥从目标应用采集，输出 OBS Virtual Camera（设置 1280×720、30 FPS）；AGI Mocap 读取虚拟摄像头并通过 VMC 发送姿态至本机动作总线，再由 Blender 的沃雅妮莎/薇斯纳订阅。用户确认 AGI 运行久后识别变差、卡顿，**仅重启 AGI** 即恢复；并未开启动作录制。

## 已观察到的证据

- 旧 AGI 进程的单骨骼更新约 25 次/秒，15 秒采样中髋/腿出现 76–89° 的单帧旋转跳变。用户手动重启后的另一进程约 57 次/秒，采样最大跳变低于 25°。这是 VMC 发送频率，不等同于模型推理帧率。
- 2026-09-24 新进程在约 4–12 分钟内私有内存从 1534 MB 到 2995 MB，线性斜率约 193 MB/分钟；屏幕桥私有内存约 550 MB、GPU 总显存占用约 3.4–3.6 GB，均未同步增长。AGI 输出包率总体下降，Blender 在同一时段也变慢。原始时间序列在 `work/agi_longrun_20260924.csv`。
- 当前 `GameAssembly.dll` 是早期项目修改过的版本，包含 `agi_dump.on` 条件调试钩子：开启时每帧覆盖写 `agi_pose.bin`。当前 VMC 链路不依赖它。两次 ABAB 测量：开约 193、192 MB/分钟；关约 118、123 MB/分钟。钩子放大内存增长，但关闭后仍有明显增长，因此不是唯一问题。原始数据在 `work/agi_dump_off_20260924.csv`、`work/agi_dump_reon_20260924.csv`、`work/agi_dump_off_again_20260924.csv`。目前开关改名为 `agi_dump.off`，可将其改回 `agi_dump.on` 重新启用旧姿态文件输出；依赖这个文件的旧 miko 方案在关闭期间不可用。
- AGI 实时设置的 PlayerPrefs 显示 `speed=1`、`skip=1`、`onHand=1`、`onFace=1`，用户确认没有录制。[官方说明](https://www.dimocap.com/upload/AGI_Mocap%E4%BD%BF%E7%94%A8%E8%AF%B4%E6%98%8E.pdf)把“加速识别”列为长时间捕捉、或手指/表情识别变慢时可开启的设置；本机加速开关已开启。软件基于 Unity 2022.3.20，进程加载 `mediapipe_c.dll` 和 GPUCompute 推理组件。现有数据不能将剩余增长准确归因于某个 DLL 或模型。
- `Mocap5.ToggleImage` 控件存在于场景资源，但 RectTransform 横坐标为 -100，当前界面正常使用时不可见；用户确认找不到图像预览开关。未修改该资源。一次短暂关闭 AGI、更改图像预览设置并重启的自动化试验被执行审查拒绝，故该设置仍为原值。

## 当前结论与边界

AGI 进程本身存在持续的私有内存增长，同时长运行输出更新率下降；用户观察到重启即恢复。补丁调试写盘是可测量的附加负担，已安全关闭，但 AGI 主程序/推理链仍有剩余增长。不能仅凭进程私有内存曲线区分真泄漏、持续缓存、内存碎片或推理积压。由于该 `GameAssembly.dll` 被修改过，不能在未用官方原版复现前把剩余增长全部归因于厂商。GPU 显存并未耗尽，句柄数未持续上升；常规硬件容量不足不是当前证据支持的主因。Blender 衣裙物理本身也可能在低帧率和姿态跳变下短暂失稳，不能把截图中的衣裙异常全归咎于 AGI。

## IL2CPP 内部路径静态检查（只读，2026-09-24）

依据当前 `GameAssembly.dll` 和已存在的 `C:/Users/mozi/decompile-tools/agi-dump/dump.cs` RVA 表，用 `work/inspect_agi_il2cpp.py` 做了 x64 直接调用清单及局部反汇编。**未修改 DLL，也未向运行中 AGI 注入代码。**

- `Mocap5.Update`（RVA `0x486A60`）调用 `Mocap5.ExecuteML`（`0x470620`）。后者从 `MainTexture` 创建 640×640、3 通道的 `TensorFloat` 输入，并调度多次模型推理。该函数包含 3 处 `TextureConverter.ToTensor`、6 处 `TensorFloat` 构造、5 处 `Tensor.TakeOwnership()`；这些是函数内的静态调用点，**不代表每一处在每帧都执行**。当前构建的模型后端常量是 GPUCompute（256）。
- 该模型输入边长在程序集里固定为 640；屏幕桥当前送 1280×720。仅提高或降低虚拟摄像头分辨率不直接改变这个固定张量尺寸，不过仍可能改变采集、缩放与摄像头驱动的开销，不能据此断定分辨率测试无用。
- `Mocap5` 持有四个张量字段：`input`（偏移 `0x338`）、`imgtensor`（`0x340`）、`imgoutput`（`0x348`）、`posetensor`（`0x350`）。`ExecuteML` 在 RVA `0x471671`、`0x473F1A`、`0x4742B6`、`0x474418` 覆盖写这些字段。函数中确实在 `0x472AC7` 及后续若干位置经虚函数释放输入与临时张量；此前“完全没有 Dispose”的猜测已被排除。对另外三个字段未在 `ExecuteML` 的直接/已识别虚调用中看到覆盖前的逐帧释放；`Mocap5.OnDestroy`（`0x47FCF0`）则明确依次释放四个当前字段。此处可能让旧张量依赖终结器/垃圾回收而延后释放。是否每帧走到这些赋值、旧对象最终是否回收，仍需要动态内存分配栈或受控功能 A/B 才能确认。
- `Tensor.Finalize`（`0x235BE10`）确实调用虚 `Dispose`，因此被覆盖的旧字段**并非已证明永久泄漏**；它们可能在 GC/终结器运行时才释放 GPU/原生资源。实测私有内存偶尔短暂回落、总体仍显著上升，与“每帧生成快于延迟回收”一致，但不是独占解释。
- [Unity Sentis 1.2 官方文档](https://docs.unity.cn/Packages/com.unity.sentis%401.2/manual/get-the-output.html)说明：`PeekOutput` 的浅引用通常由 worker 管理，但调用 `TakeOwnership` 后由调用者负责 `Dispose`。因此这组所有权调用是具体的泄漏/积压疑点，而不是仅凭进程增长做泛泛推测。
- VMC 的 `uOscClientTDP` 自身队列常量 `MaxQueueSize=100`，其 `Add` 函数（`0x4C7650`）在长度超过 100 时移出旧消息。无界 VMC 发送队列不是当前静态证据支持的原因；发送时仍会频繁创建消息和 `MemoryStream`，可能增加 GC 压力，但尚未量出其单独贡献。
- `frame3D` 等列表有大量访问，但可见的主要片段由 `VideoPlayer` 状态和录制条件控制；用户当前从 OBS 虚拟摄像头输入且没有录制，尚无证据显示这类录像列表在当前路径无界积累。
- 摄像头输入停止后 AGI 没停发 VMC、内存增长反而加速。`Update` 的 `ExecuteML` 调用点没有紧邻的“新摄像头帧才推理”检查，支持重复处理旧/空画面的可能性；但完整控制流复杂，不能凭局部反汇编断言具体重连逻辑。

**可定位的机制范围：**摄像头/RenderTexture → Sentis 张量/多个 worker → 姿态骨架 → VMC 发送。当前最高优先级是确认张量字段的逐帧所有权、特别是 `imgtensor`/`imgoutput`/`posetensor` 的覆盖前释放；其次是断流时是否继续创建张量。若拥有应用源码，应该在每帧替换前释放旧张量、给临时张量使用确定性 `Dispose`，并在没有新摄像头帧时避免重复推理。不能把这些静态疑点直接当作已验证的二进制补丁方案。
